# 保留未保存内容（草稿恢复）

状态：**待签收**（随 0.5.0 发布，未发布）

## 背景

用户反馈两件事：

- 「vs code 最大的一点就是支持关机之后新创建临时文件不会消失」：未命名文件跨重启保留。
- 「停电或者死机，内容还在吗？」：崩溃与断电不能丢未保存内容。

两者是同一套机制：把未保存的文本持续写到用户数据目录的草稿区，下次启动读回来。这也是 VS Code（hot exit + Backups）、Sublime Text（`hot_exit` + 会话文件）和 Notepad++（Session snapshot & periodic backup，默认 7 秒）的做法。

## 需求

- 设置 → 工作区新增「保留未保存内容」，**默认开启**（0.6.0 起；更早的设置文件保留用户存下的值）。关闭时行为与 0.4.1 完全一致。
- 开启后：
  - 关闭窗口 / 退出应用不再弹「保存全部 / 不保存 / 取消」，未保存的标签（含未命名文件）在下次启动恢复，并仍显示未保存标记。
  - 崩溃、强制结束、断电后同样恢复，最多丢最近约 5 秒的输入。
  - 关闭单个标签仍提示保存 / 不保存 / 取消；「不保存」真的删除草稿。
  - 「关闭时确认未保存文件」在开启期间置灰（两者语义冲突）。
  - 在设置里关闭该开关时，删除已有草稿，退出回到原来的提示流程。
- 非目标：恢复光标、选区和撤销栈；自动保存到原文件；版本历史 / 长期备份；工作区磁盘搜索。

## 存储

位置是**用户数据目录**（与 `settings.json`、`session.json`、`zpad.log` 同级），不是系统临时目录（macOS 重启会清 `/var/folders`，Windows 存储感知会清 `%TEMP%`，Linux 的 tmpfiles 会清 `/tmp`），也不写在文件旁边（避免污染工作区、只读目录写不进去）。

```
macOS    ~/Library/Application Support/ZPad/drafts/
Windows  %AppData%\ZPad\drafts\
Linux    ~/.config/ZPad/drafts/          # $XDG_CONFIG_HOME
```

（`go tool mygo dev` 使用 `ZPad Dev`，与正式版分开。）

```
drafts/
├── index.json      # 每个草稿的条目：id、路径或未命名编号、编码、文件 size/modtime、写入时间
├── 6a1f…           # 一个草稿一个文件，UTF-8 原文，保留真实换行符
└── 8bc2…
```

- 目录 `0700`，文件 `0600`。
- 草稿正文**不放进** `session.json` 或 JSON 字段：会话继续只存布局，`TabState` 只多一个草稿 id 和未命名编号。
- 写入走 `Buffer.Snapshot().WriteTo` + 新增的 `atomicfile.WriteTo`，流式落盘，不复制整份文本；否则 10 MB 文档会瞬时多出 20–30 MB 堆占用，顶高 `debug.SetGCPercent(50)` 压出的堆水位。

## 写入节奏

- 每秒检查一次已打开文档（`mygo.RunOnMain`，主线程、不重绘）。
- 停止输入 **1 秒**后写；持续输入时最多 **5 秒**写一次（与 MyGo 内置文档恢复的参数一致）。
- 只写「脏」的文档，以及有文字的未命名文档；只读文档跳过。
- 窗口关闭 / 退出前同步 `flushDrafts()`，等正在进行的写入结束后再补一次。

## 生命周期

恢复后**不立即删除**旧草稿，等它被重新写出一份或文档被保存 / 丢弃才删。

| 时机 | 处理 |
| --- | --- |
| `saveTab` 写盘成功（含另存为） | 删除草稿 |
| 退出前批量保存 `saveDocsForClose` | 每个文档写盘成功后删除 |
| 系统注销保存 `saveDirtySync` | 同上 |
| 外部修改重载 / 重新以编码打开 | 删除草稿 |
| 文档变干净（撤销回已保存状态） | 下一次扫描时删除 |
| 关闭最后一个标签 / 删除文件 | 删除草稿；同一文档还在另一栏时保留 |
| 重命名文件或目录 | 更新草稿索引里的路径（不改正文） |
| 恢复启动 | 不删除；写盘成功后才删旧副本 |
| 关闭「保留未保存内容」设置 | 停止扫描并清空草稿目录 |

并发细节：每个文档有一个 epoch，保存 / 丢弃 / 重命名时递增；写盘 goroutine 在存储锁内检查 epoch，过期的写入直接跳过，避免「保存后又被旧副本写回来」。

## 启动恢复

1. 设置开启时先打开草稿目录，读出索引。
2. 若「启动时恢复会话」也开启：按 `session.json` 的标签顺序恢复；每个标签先按草稿 id、再按路径找草稿。
3. 没有对应会话标签的草稿（会话没来得及保存、或未开启恢复会话）追加到左栏，不抢活动标签。
4. 文件存在时先按磁盘内容打开，再对比草稿：
   - 文本相同（崩溃前已经保存过）→ 丢弃草稿，按已保存打开。
   - 文本不同 → 覆盖为草稿文本，保持未保存状态；沿用草稿里的文件 size/modtime，这样崩溃期间文件被别的程序改过时，现有的外部修改检查会在下次聚焦时询问「重新加载 / 保留我的 / 另存为」。
   - 文件已被删除 → 直接从草稿建立文档，保存时走原有的「重新创建」提示。
5. 未命名编号接着最大编号继续。
6. 恢复数量通过 toast 提示「已恢复 N 个未保存的文件」。

## 测试

- `internal/draft`：写入 / 读取 / 重新打开 / 删除、不想要的写入跳过、路径迁移、清空、损坏索引另存为 `.bak`、id 安全且不重复。
- `internal/app`：未命名与已命名文档的草稿写入；带编码与 CRLF 的恢复；会话恢复未命名文件并续编号；未开启会话恢复也能恢复；文件已保存则丢弃旧草稿；保存 / 变干净 / 关闭最后一个标签时删除；同一文档还在另一栏时保留；重命名迁移；关闭设置时清空；退出保留；只读跳过；1 秒 / 5 秒节奏；崩溃期间文件被改时保留草稿 stamp；设置项与置灰状态。

## 已知限制

- 不恢复光标、选区和撤销历史，只恢复文本、编码、换行符、标签位置与滚动。
- 空白的未命名标签不写草稿（没有内容可丢），只由会话记录；崩溃时可能少一个空标签。
- 断电瞬间正在写的副本可能丢最后一次，上一份仍完整；`atomicfile` 只 `fsync` 文件不 `fsync` 目录，与现有 `session.json` / `settings.json` 一致。
- 草稿不是备份工具，不保留历史版本；保存或丢弃后即删。
- 开启后退出不再询问保存，这是 Notepad++ / Sublime / VS Code 的同一取舍；不习惯可把开关关掉。
- 关闭开关会清空草稿，包括还没处理的未保存内容，然后退出重新提示保存。
